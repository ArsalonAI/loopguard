# LoopGuard — Product Requirements Document

**Status:** Draft v1
**Owner:** Arsalon
**Last updated:** 2026-07-27
**Primary deliverable:** Research artifact + reproducible repo, with a static trace/results dashboard as the presentation layer

---

## 1. Problem statement

Multi-step tool-using agents degrade as the number of sequential reasoning hops grows, but the literature and most internal evals report this degradation as a single aggregate accuracy number. That framing is not actionable: it tells you *that* a deeper loop is worse, not *why*, and it gives no basis for choosing a mitigation or for knowing whether a mitigation actually fixed the thing it was supposed to fix.

Three specific gaps:

1. **Confounded variables.** Real benchmarks vary task semantics, tool count, and context length simultaneously with depth. Any depth-vs-accuracy curve drawn from them is uninterpretable.
2. **Unattributed failures.** "The agent got it wrong" collapses at least three mechanically distinct failure modes — fabricating a value, calling the wrong tool, and confidently using a real-but-wrong value that entered context earlier. These have different fixes.
3. **Unpriced mitigations.** Mitigations are reported as accuracy wins. They are actually trades: tokens and latency for reliability. Without the denominator, a "+8% accuracy" result is not a decision input.

LoopGuard addresses all three: a synthetic task family that isolates loop depth as the sole independent variable, a mechanically-resolved failure taxonomy, a mitigation evaluated against the specific failure mode it targets, and a cost-priced result.

---

## 2. Goals

**G1.** Produce a depth-vs-failure curve for 2 open-weight models where loop depth is the only variable that changes, with everything else (task semantics, tool count, distractor density, per-hop payload size, prompt template) held constant by construction.

**G2.** Attribute every failed episode to a failure mode using ground truth from the task generator, falling back to an LLM judge only for the residual that ground truth cannot resolve — with judge/human agreement measured and reported, not assumed.

**G3.** Identify the dominant failure mode per depth from an unmitigated baseline, then select and test exactly one mitigation chosen *because* it targets that mode, and report its effect on that failure category specifically.

**G4.** Report the mitigation's token and latency overhead alongside its failure-rate reduction, so the result reads as a priced tradeoff.

**G5.** Ship a regression CLI that diffs failure rates between two runs (agent versions or configs) and returns a non-zero exit code when a reliability regression exceeds a configured threshold, suitable for a CI gate.

**G6.** Ship a static dashboard that renders the run artifacts — depth curves, failure-mode breakdowns, individual trace inspection, and run-to-run diffs — deployable to S3/CloudFront with no backend.

### Non-goals

- Benchmarking closed/frontier models. Two open-weight models is the scope.
- Realistic or naturalistic tasks. Synthetic and controlled is the *point*; external validity is explicitly traded away for internal validity and is stated as a limitation.
- Testing more than one mitigation. A second mitigation is a stretch goal, not a commitment.
- Any live inference from the dashboard. The dashboard reads artifacts; it does not run agents.
- Training, fine-tuning, or model-side interventions.

## 3. Experimental design

### 3.1 Independent variable

**Loop depth `d`** — the number of sequential tool calls required to resolve the task. Range: `d ∈ {1, 2, 3, 4, 5}`.

### 3.2 Held constant by construction

These are the design's load-bearing controls. A change to any of them across depth invalidates the curve.

| Held constant | Mechanism |
|---|---|
| Tool set size | The same `N` tools are exposed at every depth (`N` fixed, `N > d_max`). Depth changes how many are *needed*, never how many are *available*. |
| Distractor density | Fixed number of distractor entities per hop, generated by the same perturbation rules at every depth. |
| Per-hop payload size | Tool responses are schema-identical and length-matched (±10% tokens) across hops and depths. |
| Task semantics | One task template. Depth `d=5` is the same *kind* of question as `d=1`, just chained further. |
| Prompt / system message | Byte-identical across all conditions except the mitigation arm. |
| Decoding params | Fixed temperature, top_p, max_tokens, and seed policy across all conditions. |

**Known and accepted confound:** context length grows with depth, because more hops means more tool output in the transcript. This is intrinsic to the construct — you cannot increase loop depth without accumulating context. It is documented as a limitation rather than papered over. A stretch-goal control arm (context-length-matched padding at low depth) is defined in §10.

### 3.3 Task family: chained entity lookup

A synthetic entity graph. Each task is a chain: start from a seed entity, resolve an attribute that names the next entity, repeat `d` times, and report a terminal attribute.

```
Question (d=3):
  "What is the escalation contact for the region that owns
   the datacenter hosting service SVC-4471?"

Ground-truth chain:
  hop 1: lookup_service("SVC-4471")       → datacenter: DC-NORTH-12
  hop 2: lookup_datacenter("DC-NORTH-12") → region: REG-EMEA-3
  hop 3: lookup_region("REG-EMEA-3")      → escalation_contact: "j.okafor@..."
```

**Distractor entities.** Each hop's response includes plausible-but-wrong sibling records generated by controlled perturbation of the correct record:
- *Near-ID distractors* — IDs at edit distance 1–2 from the correct one (`DC-NORTH-12` vs `DC-NORTH-13`).
- *Cross-branch distractors* — valid entities from a different chain that share a field value with the correct one.
- *Stale distractors* — entities carrying an attribute name matching an *earlier* hop's, to bait premature answering.

Distractor design is what makes the task non-trivially failable, and it is the primary difficulty knob.

**Tool set.** `N` tools exposed, of which `d` are needed. Non-required tools are semantically adjacent and schema-plausible (e.g. `lookup_service_legacy`, `search_entities`, `list_regions`) so that tool selection is a real decision rather than a trivial one. Tools are deterministic pure functions over the generated graph — no network, no nondeterminism, fully replayable.

**Generation.** A seeded generator produces the graph, chain, distractors, and gold trace together, so ground truth for *every intermediate step* is known — not just the final answer. This is what enables mechanical failure attribution (§4).

### 3.4 Difficulty calibration

A task family that every model solves, or that no model solves, produces a flat curve and no information.

**Calibration protocol (Phase 1, before any headline runs):**
1. Run a pilot of ~30 tasks at `d=3` on both models with a starting distractor configuration.
2. **Target:** baseline failure rate in the **20–60%** band at `d=3` for at least one model, and non-zero-non-total for both.
3. If outside the band, adjust *only the distractor knobs* — count per hop, ID edit distance, cross-branch overlap rate — never the chain structure, tool count, or prompt.
4. Freeze the configuration. Record it as `calibration.lock.json`, committed. All headline runs use the frozen config.
5. Pilot traces are discarded from all reported results.

**Explicit hazard:** calibration must not be re-run after seeing headline results. Freezing the config to a committed file and reporting the pilot separately is the guard.

### 3.5 Run matrix (baseline)

| Factor | Levels |
|---|---|
| Depth | 1, 2, 3, 4, 5 |
| Model | Llama 3.3, Qwen3 |
| Tasks per cell | 40 (distinct generator seeds) |
| Repeats per task | 3 (decoding seeds) |

= **1,200 baseline episodes.** The mitigation arm re-runs the same task seeds under the mitigation config; identical task instances across arms means paired comparison, which is materially tighter than independent samples.

**Serving:** hosted OpenAI-compatible endpoints (Together / Groq / Fireworks — provider selected at Phase 0 on tool-calling fidelity and rate limits). Consequences accepted and handled:
- Latency is network-bound and noisy → report **median and p90 wall-clock across ≥3 repeats**, and additionally report **generated-token count** as the provider-independent cost proxy. Token overhead is the primary cost claim; latency is secondary and explicitly caveated.
- Provider-side nondeterminism means seeds do not guarantee bit-identical output → this is why every cell is repeated 3×, and why all raw traces are archived for replay.
- Model version pinning: the exact provider model string and any served revision is recorded in every run manifest.

**Statistics:** Wilson score intervals on all proportions. Depth effect tested with a trend test across depths. Mitigation effect tested paired (McNemar on per-task success flips) on the targeted failure category. Report effect sizes and intervals; with n=40 tasks/cell, small differences will not be resolvable and the writeup must say so rather than narrating noise.

## 4. Failure taxonomy

### 4.1 Categories

| Code | Category | Definition |
|---|---|---|
| `CORRECT` | Success | Final answer matches gold terminal attribute. |
| `HALLUCINATION` | Fabrication | Final answer, or a value used to drive a tool call, does not appear anywhere in the transcript's returned tool output. Invented from nothing. |
| `TOOL_MISUSE` | Wrong tool operation | Wrong tool for the hop, malformed/schema-invalid arguments, argument referencing a non-existent entity, or a tool call whose domain cannot serve the current hop. |
| `CONTEXT_POLLUTION` | Real-but-wrong value | The agent used a value that *did* appear in context but belongs to a distractor or an earlier hop — including premature termination on a stale intermediate value. Distinct from hallucination: the value is real, the selection is wrong. |
| `NON_TERMINATION` | Budget exhaustion | Hit max-steps or max-tokens without producing a final answer; includes repeated identical tool calls. |
| `AMBIGUOUS` | Unresolved | Ground-truth comparison does not cleanly assign a category. Routed to the LLM judge (§4.3). |

Categories are assigned to the **first divergence from the gold trace**, not the final answer alone. An episode that goes wrong at hop 2 and then behaves reasonably is a hop-2 failure. `first_error_hop` is recorded on every episode and is a first-class reported quantity — it is the strongest available signal for whether depth degrades reasoning or merely gives it more chances to fail.

### 4.2 Mechanical resolution (primary path)

Because the generator emits the gold trace, most attribution is deterministic string/set comparison — no model in the loop:

- Every tool call in the trace is compared against the gold call for that hop → tool identity and argument correctness.
- Every value the agent emits is checked for membership in the set of values actually returned by tools → separates fabricated from context-sourced.
- Context-sourced wrong values are checked against the known distractor registry → confirms pollution and identifies *which* distractor type won.

**Requirement:** ≥80% of failed episodes must be mechanically resolved. If the ambiguous residual exceeds 20%, the resolver is under-specified and must be improved before the judge is leaned on — a large residual means the taxonomy is being decided by a model, which is the thing this design is trying to avoid.

### 4.3 LLM judge (residual only) and its calibration

The judge sees only `AMBIGUOUS` episodes. It is never used to grade correctness — correctness is exact-match against gold.

**Calibration is a deliverable, not an assumption:**
1. Hand-label a stratified subset of **≥100 episodes** (spanning all depths, both models, mechanically-resolved and ambiguous).
2. Run the judge blind on the same subset.
3. Report **Cohen's κ** and raw percent agreement, per category, in the final writeup.
4. **Gate:** κ ≥ 0.70 to use judge labels in headline numbers. Below that, the judge output is reported as exploratory only and the residual is reported as an explicit `UNRESOLVED` bucket rather than silently absorbed.
5. The hand-labeled set is committed as a fixture and doubles as a regression test for judge-prompt changes.

Judge model, prompt, and version are pinned and recorded in the run manifest.

## 5. Phases and deliverables

### Phase 0 — Scaffolding
- Repo structure, config schema, provider client behind one interface, run-manifest format (model string, decoding params, config hash, git SHA, timestamp, provider).
- Trace format: append-only JSONL per episode capturing every message, tool call, tool response, token counts, and per-step wall-clock.
- Provider smoke test: verify tool-calling fidelity on both models before committing to a provider.

**Exit:** one end-to-end episode runs against both models and writes a valid trace.

### Phase 1 — Task family + calibration
- Seeded graph/chain/distractor generator with gold-trace emission.
- Tool implementations as pure functions over the graph.
- Pilot runs and calibration to the 20–60% band; `calibration.lock.json` frozen and committed.

**Exit:** frozen config, documented pilot results, generator unit tests (chain validity, distractor uniqueness, payload length-matching).

### Phase 2 — Baseline run + taxonomy
- Execute the 1,200-episode matrix.
- Mechanical resolver; measure the ambiguous residual and iterate until <20%.
- Hand-label ≥100 episodes; run and calibrate the judge; report κ.

**Exit:** per-depth, per-model failure-mode distributions with Wilson intervals; `first_error_hop` distributions; documented judge agreement.

### Phase 3 — Diagnosis + mitigation
- Identify the dominant failure mode per depth, and the depth at which failure rate first crosses a meaningful threshold.
- **Select one mitigation, data-driven.** Per direction, no candidate mitigation is named in this PRD. Selection is governed by criteria only (§6).
- Re-run the mitigation arm on the *same task seeds* (paired).

**Exit:** paired comparison on the targeted failure category, plus aggregate accuracy as a secondary number.

### Phase 4 — Cost accounting
- Token overhead (prompt + completion, per episode, by depth) and latency overhead (median, p90) for the mitigation arm vs baseline.
- Framed as: *reliability points bought per 1k additional tokens*, per depth.

**Exit:** the tradeoff table (§7).

### Phase 5 — Regression CLI
See §8.

### Phase 6 — Dashboard
See §9.

### Phase 7 — Writeup
- Findings, method, judge calibration, limitations (synthetic-only, context-length confound, 2 models, n=40/cell, hosted-inference latency noise).
- **Judge provenance limitation.** Every model under test is open-weight, but the judge may be a closed model (TRD §14). Exact replication of judge-assigned labels therefore requires that vendor's access. Two things bound the damage and both are committed to the repo: the judge touches only the ambiguous residual (≤20% of failures, §4.2), and the hand-labeled calibration fixture plus the reported κ let anyone check the judge's quality — or substitute their own judge and re-derive the residual — without trusting it.

## 6. Mitigation selection criteria

The mitigation is chosen after baseline results land. This PRD fixes the *rules*, not the answer:

- **C1 — Targeting.** The mitigation must have a stated causal mechanism against the *dominant* failure mode identified in Phase 3. The mechanism is written down *before* the mitigation arm runs, in a pre-registration note committed to the repo.
- **C2 — Isolation.** The mitigation changes exactly one thing. It must not simultaneously alter the prompt, the tool set, and the control flow.
- **C3 — Measurable on-target.** The primary outcome is the rate of the *targeted category*, not aggregate accuracy. Aggregate accuracy is reported second.
- **C4 — Off-target reporting.** Rates for all non-targeted categories are reported too. A mitigation that cuts its target mode while inflating another is a real and interesting result, and must not be hidden by an aggregate win.
- **C5 — Priced.** It must be measurable in tokens and latency (§7). Anything unpriceable is out of scope.
- **C6 — Falsifiable prediction.** The pre-registration note states the expected direction and rough magnitude. A mitigation that "works" for reasons unrelated to its stated mechanism is flagged as such.

## 7. Cost accounting

Reported per depth, mitigation arm vs baseline:

| Metric | Definition |
|---|---|
| Δ targeted-failure rate | Primary outcome, paired, with CI |
| Δ aggregate success rate | Secondary |
| Δ off-target failure rates | All other categories, to catch displacement |
| Δ prompt tokens / Δ completion tokens | Per episode, mean and p90 |
| Δ tool calls | Per episode |
| Δ latency | Median and p90 wall-clock, explicitly caveated as hosted-inference-noisy |
| **Reliability per 1k tokens** | (Δ failure-rate reduction) / (Δ total tokens per episode / 1000) |

The headline framing is a priced tradeoff, e.g. *"cuts context-pollution failures at d=5 by X points at a cost of Y% more tokens and Z ms p90 latency"* — never a bare accuracy delta.

## 8. Regression CLI

```bash
loopguard run    --config configs/baseline.yaml --out runs/2026-07-27-baseline
loopguard grade  runs/2026-07-27-baseline          # mechanical + judge attribution
loopguard report runs/2026-07-27-baseline          # tables, curves, JSON summary
loopguard diff   runs/<baseline> runs/<candidate>  # per-category, per-depth deltas
loopguard gate   runs/<baseline> runs/<candidate> --policy policy.yaml
```

**`diff`** — per-depth, per-model, per-failure-category rate deltas with CIs. Paired when both runs share task seeds (detected from manifests), unpaired otherwise, and it states which mode it used. Text table and JSON output.

**`gate`** — the CI entry point. Reads a policy file:

```yaml
thresholds:
  aggregate_failure_rate:      { max_increase_pp: 3.0 }
  category.CONTEXT_POLLUTION:  { max_increase_pp: 2.0 }
  category.HALLUCINATION:      { max_increase_pp: 1.0 }
  per_depth:
    "5": { max_increase_pp: 5.0 }
require_significance: true    # only fail on deltas whose CI excludes zero
min_episodes: 200             # refuse to gate on an underpowered run
```

**Exit codes:** `0` pass · `1` regression exceeding threshold · `2` insufficient data to decide (underpowered run — this must *not* silently pass) · `3` config/run error.

`require_significance` exists to stop the gate flapping on noise; `min_episodes` exists to stop it passing vacuously on a truncated run. Both are load-bearing for CI trust.

**CI integration:** a GitHub Actions workflow that runs a reduced matrix (fewer seeds) on PRs touching agent code, and the full matrix nightly.

## 9. Dashboard

Static single-page app. **No backend, no server-side inference.** It reads the JSON artifacts a run produces. This is what makes it deployable to S3 + CloudFront as static files and what keeps it in scope.

**Views:**
1. **Depth curve** — failure rate vs depth, one line per model, CI bands.
2. **Failure composition** — stacked bars by depth and model, showing how the taxonomy mix shifts with depth. This is the core visual of the whole project.
3. **Trace inspector** — pick an episode, step through it; each step shows the agent's tool call beside the gold call, with the **first divergence highlighted** and the assigned failure category shown with its resolution source (mechanical vs judge).
4. **Run diff** — the `loopguard diff` output rendered: two runs side by side, per-category deltas, significance flags.
5. **Method panel** — frozen calibration config, judge κ, run manifests. Reproducibility surfaced, not buried in the repo.

**Build:** Vite + React, static export. Run artifacts published alongside as JSON. Deployment target S3 + CloudFront; `aws s3 sync` in a make target. Local usability (`vite preview` against a run directory) is a hard requirement — deployment is optional convenience, never a prerequisite for using it.

**Explicitly deferred:** live agent execution from the browser (the "sandbox" idea), auth, multi-tenant run storage, a query backend. These turn a static site into a service and are out of scope. Noted in §10 as the natural v2.

## 10. Risks and open items

| Risk | Mitigation |
|---|---|
| Calibration lands degenerate (0% or 100% failure) | Distractor knobs are the tuning surface; calibration budget is explicitly allocated in Phase 1. If `d=5` saturates at 100% for both models, the depth range shifts down rather than the task changing. |
| Context length confounds depth | Documented as intrinsic. Stretch: a padded-context control arm at low depth to separate "more hops" from "more tokens". |
| Ambiguous residual too large → judge does the real work | Hard gate at 20%; resolver improved before proceeding. |
| Judge κ below 0.70 | Judge labels demoted to exploratory; residual reported as an explicit `UNRESOLVED` bucket. Pre-committed so it isn't a mid-project judgment call. |
| Hosted-inference latency noise swamps the latency claim | Token overhead is the primary cost metric; latency is secondary, reported as median/p90 across repeats, and caveated. |
| Provider tool-calling quirks differ between the two models | Phase 0 smoke test before provider commitment; any per-model prompt adaptation is documented as a deviation from "byte-identical prompt". |
| n=40/cell underpowers small effects | Stated up front. The writeup reports intervals and declines to narrate differences the data cannot resolve. |
| Scope: dashboard plus full study in one pass | Dashboard is static-artifact-driven and last in sequence. If scope must be cut, Phases 6 then 5 are the cut lines — the study and taxonomy are the deliverable. |

**Open items for later decision (do not block Phase 0):**
- Exact `N` for tool-set size — set during Phase 1 calibration.
- Provider choice — Phase 0.
- Whether a second mitigation arm fits — reassess after Phase 4.
- Live sandbox / interactive agent execution in the dashboard — v2.

## 11. Success criteria

The project succeeds if, at completion:

1. A depth-vs-failure curve exists for both models where depth is the only manipulated variable, with the held-constant controls verifiable from committed config.
2. Failures are attributed to modes, ≥80% mechanically, with judge agreement measured and reported.
3. The dominant failure mode per depth is identified and stated.
4. One mitigation, chosen for and pre-registered against that mode, has been tested paired, and its effect on the targeted category is reported alongside off-target effects.
5. That effect is priced in tokens and latency.
6. `loopguard gate` runs in CI and fails a deliberately-introduced regression.
7. The dashboard renders the run and lets a reader step through a failed trace to its first divergence.

A negative result — the mitigation doesn't help, or helps only by displacing failures into another category — satisfies these criteria. The deliverable is a trustworthy measurement, not a win.
